## Intent and defaults

Phase 4 adds **monthly assessments**: a self-check testing feature the
student uses to quiz themselves, not a stand-in for a real school exam
administered by a teacher. The human partner opted out of the brainstorming
questions for this phase, so the following significant choices are mine,
stated explicitly rather than implied:

- **Self-authored question bank, not externally sourced or AI-generated.**
  The student builds their own bank of questions per subject (consistent
  with the project's no-fabricated-data ethos carried over from Phase 2/3 —
  there is no question-generation service, no imported question sets).
- **Two question types: multiple-choice and short-answer**, both
  auto-graded by exact match (short-answer: case-insensitive, trimmed).
  No free-text/essay grading, no AI grading — that would require judgment
  calls this app has no mechanism to make honestly.
- **"Monthly" is cadence guidance, not an enforced schedule.** A student
  can take a test whenever they want; nothing locks them to once a month.
  The dashboard nudges based on time since the last test, mirroring how
  Phase 2's plan already nudges on daily activity.
- **Weak-topic analysis via a required `topic` tag per question**, not
  NLP/semantic analysis of free text. Each question belongs to a subject
  and, within it, a topic (e.g. subject "Math", topic "Fractions"). Wrong-
  answer rate is aggregated per topic across all completed tests.
- **One subject per test.** A test is generated by picking up to N
  questions (default 10, or fewer if the bank has fewer) at random from one
  subject's bank — mirrors Phase 2's plan generator picking from one
  student's tasks/goals, keeps scope and results legible ("how am I doing
  in Math" rather than a muddled cross-subject score).

## Data model

Three new tables, all scoped to `studentProfileId` (never a bare `userId`
or client-supplied id), following the exact ownership-check discipline
every Phase 1-3 server action already uses: resolve the acting student from
`getCurrentSessionUser()` → `StudentProfile` inside the server action,
never trust a client-supplied id; any by-id mutator verifies the target
row's `studentProfileId` matches the caller's own profile and returns a
generic "not found" on mismatch.

- **`Question`** — `id`, `studentProfileId`, `subjectId`, `topic` (string,
  required, free text — e.g. "Fractions"), `type` (`"mcq"` |
  `"short_answer"`), `prompt` (string), `options` (string, JSON-encoded
  array — only meaningful for `mcq`; empty/unused for `short_answer`),
  `correctAnswer` (string — for `mcq` this must equal one of `options`
  verbatim; for `short_answer` it's the reference answer matched
  case-insensitively and trimmed), `createdAt`, `updatedAt`.
  `@@index([studentProfileId, subjectId])`.
- **`Test`** — `id`, `studentProfileId`, `subjectId`, `status`
  (`"in_progress"` | `"completed"`), `createdAt`, `completedAt` (nullable
  until submitted), `scorePercent` (nullable until submitted — an Int
  0-100, computed and stored at submission so historical scores never
  silently change if questions are later edited/deleted).
  `@@index([studentProfileId, createdAt])`.
- **`TestAnswer`** — `id`, `testId`, `questionId`, a **snapshot** of the
  question content at test-creation time (`promptSnapshot`,
  `optionsSnapshot`, `correctAnswerSnapshot`, `topicSnapshot`) so editing or
  deleting a `Question` after a test was generated never changes what that
  past test actually asked or how it was graded, `answerGiven` (nullable
  until the student answers), `isCorrect` (nullable until graded),
  `order` (Int, the question's position in this test). `@@index([testId])`.
  The `questionId` foreign key is nullable with `onDelete: SetNull` — the
  snapshot is the source of truth for display/grading; `questionId` is kept
  only as a "jump back to this question in the bank" convenience link.

This snapshot design is the one real architectural decision beyond Phase
2/3's established patterns: Phase 2's `PlanEntry` does NOT snapshot its
`Task`/`Goal` content (it reads live via the relation), which is correct
there because a task's title changing mid-day should show the current
title. A test's fairness/history depends on the opposite property — a
score from three weeks ago must keep meaning what it meant then, even if
the student has since fixed a typo in that question or deleted it outright
to replace it with a better one.

## Pages in scope

- **`/questions`** — question bank management. Per-subject list (reusing
  the existing `Subject` records from onboarding — no new subject concept),
  add/edit/delete a question, a simple form for `type`/`prompt`/`topic`
  and (for `mcq`) 2-6 `options` plus which one is correct. Empty state per
  subject: "No questions yet for &lt;subject&gt; — add one to start building
  a test."
- **`/tests`** — history list (subject, date, score%) newest first, a "Start
  a new test" control (pick a subject, pick question count up to the
  bank's size, defaulting to 10), and the weak-topics summary (topics
  with the highest wrong-answer rate across all completed tests, minimum
  2 attempted questions in that topic to avoid single-question noise —
  honestly shows "Not enough data yet" below that threshold rather than a
  misleading 100%-or-0% topic from one lucky/unlucky guess).
- **`/tests/[id]`** — a single test. While `in_progress`: one page listing
  every `TestAnswer`'s snapshot prompt with an input (radio buttons for
  `mcq`, a text field for `short_answer`), one "Submit test" action that
  grades every answer at once and marks the test `completed`. While
  `completed`: read-only review — each question's snapshot, the student's
  answer, the correct answer, and whether it was right, plus the overall
  score.
- **`/dashboard`** modification: a new "Monthly tests" card, following the
  exact pattern of Phase 2/3's cards — real data only (most recent score,
  or "No tests yet" / a nudge based on days since the last completed test),
  linking to `/tests`.

## Out of scope for Phase 4

Teacher- or parent-authored questions, shared/public question banks,
AI-generated or imported questions, essay/free-text grading, timed tests,
multi-subject tests, a forced monthly schedule or reminder notification
(Phase 5 owns reminders generally), partial credit, question difficulty
levels or adaptive selection. Any of these could become a later phase;
none are needed for an honest, functioning self-check test.

## Testing

Vitest unit tests for the pure functions: grading a `TestAnswer` given its
snapshot and `answerGiven` (mcq exact match; short-answer case-insensitive
trimmed match); computing a test's overall `scorePercent`; the weak-topic
aggregation function (given a set of graded `TestAnswer` snapshots →
per-topic wrong-rate, honoring the 2-attempt minimum). Prisma-mocked tests
for the data-layer functions (`createQuestion`/`updateQuestion`/
`deleteQuestion`, `startTest`/`submitTest`), each with an explicit
cross-student-access test following the pattern already established in
every prior phase's data module. React Testing Library for `/questions`'
CRUD interactions and `/tests/[id]`'s answer-then-submit flow, including
the empty-bank and not-enough-data-for-weak-topics states.

None new. This phase introduces no external service.
