# Phase 4 — Monthly Assessments Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a self-check testing feature — a per-subject question bank, randomly-generated tests scored on submission, and weak-topic analysis from wrong answers.

**Architecture:** Three new Prisma models (`Question`, `Test`, `TestAnswer`) layered on the existing `StudentProfile`/`Subject` schema. A pure-function layer (grading, scoring, weak-topic aggregation, random question selection) with zero DB dependency, tested in isolation. A `"use server"` data layer (`questions.ts`, `testService.ts`) that is the only thing touching Prisma, following the exact ownership-check pattern every prior phase uses (`getCurrentSessionUser()` → `StudentProfile`, never a client-supplied id; `assertOwnedX` helpers on every by-id mutator). Three new pages (`/questions`, `/tests`, `/tests/[id]`) plus one dashboard card.

**Tech Stack:** Next.js 15 App Router, TypeScript, Prisma/SQLite, Vitest + React Testing Library — identical to Phases 1-3, no new dependencies.

**Spec:** `docs/superpowers/specs/2026-10-23-phase4-assessments-design.md`

## Global Constraints

- Every new table is scoped to `studentProfileId`; every server action resolves the acting student from `getCurrentSessionUser()` → `StudentProfile` internally, never trusts a client-supplied id (see every prior phase's `getOwnProfile()` helper, e.g. `src/lib/tasks/tasks.ts:23-27`).
- Every by-id mutator/query verifies the target row's `studentProfileId` (directly, or via its `Test`'s `studentProfileId` for `TestAnswer`) matches the caller's own profile, returning a generic "not found" on mismatch — mirrors `assertOwnedTask`/`assertOwnedSubject` in `src/lib/tasks/tasks.ts:69-80`.
- `TestAnswer` snapshots the question's content (`promptSnapshot`, `optionsSnapshot`, `correctAnswerSnapshot`, `topicSnapshot`, `typeSnapshot`) at test-creation time — a `Question` edited or deleted after a test was generated must never change what that past test asked or how it was graded. `questionId` is nullable with `onDelete: SetNull`, kept only as a "jump back to the bank" link.
- One subject per test. A test is generated by picking up to N questions (student-chosen count, clamped to however many the subject's bank actually has) at random.
- `mcq` grading is an exact string match against `correctAnswer`/`correctAnswerSnapshot`. `short_answer` grading is case-insensitive and trimmed. No AI/fuzzy grading.
- Weak-topic analysis aggregates wrong-answer rate per `topic` across all **completed** tests, with a minimum of 2 attempts in that topic before it's surfaced — below that, it's honestly "not enough data," never a misleading 100%/0%.
- Pastel pink/lavender/cream theme, existing card pattern (`rounded-xl bg-white p-6 shadow-sm`, `text-pink-dark` headings, `text-lavender-dark` subheadings/links) — no new design system.
- Dates: none of this phase's new data is a calendar date requiring UTC-midnight anchoring (`Test.createdAt`/`completedAt` are real instants, not calendar dates) — `todayInTimezone` is not needed here. When displaying `completedAt`/`createdAt` to the user, use a normal instant-aware format (e.g. `toLocaleString()` is fine — this is NOT the UTC-date-anchoring case Phase 3's final review caught, because these are real timestamps, not stored calendar dates).

## Review Focus

- **Submitting a test twice** (double-click, or resubmitting a URL after already completing it) must not re-grade, re-score, or overwrite `completedAt`/`scorePercent` a second time — `submitTest` must reject with an error on an already-`completed` test. (Review Focus item owned by Task 4.)
- **A `testAnswerId` in the submission payload that doesn't belong to the `testId` being submitted** (tampered client request, or a stale form from a different test) must not grade/update a row outside that test — `submitTest` must verify every answer's `testAnswerId` resolves to a `TestAnswer` whose `testId` matches. (Task 4.)
- **A subject with zero questions** must produce an honest "add some questions first" message from `startTest`, never an empty/broken test. (Task 4, Task 7.)
- **An MCQ question edited after a test was generated** (option text or correct answer changed) must not retroactively change that test's grading — the snapshot, not the live `Question` row, is what grading reads. (Task 1's schema design, exercised by Task 4's tests.)
- **A student with a correct guess on a single question in some topic** must not show that topic as "100% weak" or "0% weak" — the 2-attempt minimum in `computeWeakTopics` must suppress it, with a test asserting a 1-attempt topic is absent from the result. (Task 3.)

  subjectId        String
  status           String    @default("in_progress") // "in_progress" | "completed"

  createdAt        DateTime  @default(now())

  studentProfile StudentProfile @relation(fields: [studentProfileId], references: [id], onDelete: Cascade)
  subject        Subject        @relation(fields: [subjectId], references: [id], onDelete: Cascade)
  answers        TestAnswer[]

  @@index([studentProfileId, createdAt])
}

model TestAnswer {
  id                    String   @id @default(cuid())

  questionId            String?
